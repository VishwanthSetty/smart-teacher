# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## What this is

Production-grade boilerplate for the **Smart Teacher** platform. Scaffolding only — auth, RBAC, health checks, and a dashboard shell exist. No domain features (schools, classes, enrollments, timetables, videos) are implemented yet.

**Prime directive:** mirror the existing NestJS module and Next.js App Router patterns. Do not introduce a new pattern, library, or folder convention when an established one already covers the case. If you believe a new pattern is genuinely warranted, say so and explain why before writing the code.

## Monorepo layout

npm workspaces + Turborepo. Root scripts fan out to workspaces via `turbo`.

| Path | Purpose |
| --- | --- |
| `apps/api` | NestJS + Prisma + PostgreSQL REST API (port 4000). Swagger at `/api/docs`, health at `/health`. |
| `apps/web` | Next.js App Router + Tailwind (port 3000). |
| `packages/shared-types` | `Role` enum + shared interfaces, imported as `@smart-teacher/shared-types`. |
| `packages/tsconfig` | Base TS configs, imported as `@smart-teacher/tsconfig`. |

> **Sync requirement:** the `Role` enum in `shared-types` **mirrors** `apps/api/prisma/schema.prisma`, which is the source of truth. Keep them in sync manually — there is no codegen for this.

## Local dev setup

Postgres runs in Docker; apps run natively for hot reload.

```bash
cp .env.example .env                    # docker-compose vars (Postgres + container defaults)
docker compose up -d postgres
npm install
cp apps/api/.env.example apps/api/.env  # DATABASE_URL must point at localhost:5432
cp apps/web/.env.example apps/web/.env
npm run db:migrate && npm run db:seed
npm run dev
```

**Two layers of env files.** Root `.env` feeds `docker-compose.yml` (Postgres creds + container defaults). `apps/api/.env` and `apps/web/.env` feed the natively-run apps.

The API validates its env at boot via `apps/api/src/config/env.validation.ts` (class-validator) — a missing or invalid var throws on startup. Use `ConfigService.getOrThrow` everywhere downstream; never read `process.env` directly outside the config module.

**Seeded accounts** (`apps/api/prisma/seed.ts`), password `Passw0rd!`:
- `admin@smartteacher.dev` — ADMIN
- `teacher@smartteacher.dev` — TEACHER

`GET /admin/users` returns `200` for ADMIN, `403` for TEACHER. This is the reference example of RBAC — copy its shape.

## Auth architecture

Custom JWT auth with Passport strategies. Two token types, both carrying the same `AuthenticatedUser` payload (`sub`, `email`, `name`, `role`):

- **Access token** (`JWT_ACCESS_SECRET`, ~15m) — for API calls.
- **Refresh token** (`JWT_REFRESH_SECRET`, ~7d) — a bcrypt hash is stored on `User.refreshTokenHash`. `POST /auth/refresh` verifies the presented token against that hash and rotates both tokens. `POST /auth/logout` nulls the hash.

Guards and strategies live in `apps/api/src/auth`. RBAC is the `@Roles(Role.ADMIN)` decorator (`common/decorators/roles.decorator.ts`) enforced by `RolesGuard` (`common/guards/roles.guard.ts`), applied alongside `JwtAuthGuard`:

```ts
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(Role.ADMIN)
```

See `admin-users.controller.ts`. **A controller with no `@Roles` passes the guard** — so every new protected controller must declare its roles explicitly. Treat an undeclared route as a bug, not a default.

### Web ↔ API token flow (non-obvious)

The browser never sees JWTs. The Next.js app acts as a **BFF**:

1. Login page POSTs to the Next.js route `apps/web/src/app/api/auth/login/route.ts`.
2. That route calls the NestJS API (`lib/api-client.ts` → `API_URL`, default `http://localhost:4000`), receives the token pair, and stores both in **httpOnly cookies** (`lib/session.ts`).
3. Server components (e.g. `dashboard/page.tsx`) read the access token from cookies and call the API server-side.
4. `middleware.ts` gates `/dashboard/*` on presence of the access-token cookie — **existence check only, no verification**. Real authorization always happens at the API.

All API access from the web app is server-side. `API_URL` is `http://api:4000` in Docker (service name), `http://localhost:4000` locally.

## Folder structure

Keep the tree predictable. A new developer should be able to guess a file's location without searching.

### `apps/api` — feature-module structure

Each domain feature is a **self-contained NestJS module**. Never scatter a feature's files across shared folders.

```
apps/api/src/
├── main.ts
├── app.module.ts
├── config/                  # env validation, typed config
├── common/                  # cross-cutting only — no domain logic
│   ├── decorators/
│   ├── filters/
│   ├── guards/
│   ├── interceptors/
│   └── pipes/
├── prisma/                  # PrismaService + module
├── auth/                    # reference module — copy this shape
└── <feature>/               # e.g. schools, classes, timetables, videos
    ├── <feature>.module.ts
    ├── <feature>.controller.ts
    ├── <feature>.service.ts
    ├── <feature>.repository.ts   # only if data access is non-trivial
    ├── dto/
    │   ├── create-<feature>.dto.ts
    │   └── update-<feature>.dto.ts
    ├── entities/            # response shapes / serializers
    └── <feature>.service.spec.ts
```

Rules:
- **`common/` is for cross-cutting concerns only.** If it references a domain concept, it belongs in that feature's folder.
- A feature module exports only what other modules genuinely need — usually the service, never the repository.
- Cross-feature imports go through the exported service. Never reach into another feature's repository or Prisma calls directly.
- No barrel `index.ts` files inside `apps/api` — they obscure dependency graphs and break Nest's DI ordering in subtle ways. Barrels are fine in `packages/*`.

### `apps/web` — App Router structure

```
apps/web/src/
├── app/
│   ├── (auth)/              # route groups for layout boundaries
│   ├── (dashboard)/
│   │   └── <feature>/
│   │       ├── page.tsx     # server component — data fetching
│   │       ├── loading.tsx
│   │       └── _components/ # route-private components
│   └── api/                 # BFF route handlers only
├── components/
│   ├── ui/                  # primitives (button, input, table)
│   └── <shared>/            # composed, reused across routes
├── lib/                     # api-client, session, utils
└── hooks/
```

Rules:
- **Server components by default.** Add `'use client'` only when you need state, effects, or browser APIs — and push it as far down the tree as possible.
- Components used by exactly one route live in that route's `_components/`. Promote to `components/` only on second use.
- All API calls go through `lib/api-client.ts`. No raw `fetch` to the API scattered in components.

### Naming

| Thing | Convention | Example |
| --- | --- | --- |
| Files (api) | `kebab-case.<type>.ts` | `create-school.dto.ts` |
| Files (web components) | `kebab-case.tsx` | `student-table.tsx` |
| Classes / components | `PascalCase` | `SchoolsService`, `StudentTable` |
| Variables / functions | `camelCase` | `findAllByTenant` |
| Constants | `SCREAMING_SNAKE_CASE` | `MAX_IMPORT_ROWS` |
| DB tables/columns | `snake_case` via `@map` | `school_id` |
| Booleans | `is` / `has` / `can` prefix | `isActive`, `canPublish` |

## Code standards

### TypeScript
- **`strict` is non-negotiable.** No `any`. If a type is genuinely unknown, use `unknown` and narrow it.
- No `@ts-ignore`. Use `@ts-expect-error` with a comment explaining why, if truly unavoidable.
- No non-null assertions (`!`) — narrow properly or throw with a meaningful error.
- Prefer `type` for unions/shapes, `interface` for object contracts that may be extended.
- Return types are explicit on all exported functions and every public service method.

### Layering (API)

Strict, one-directional flow:

```
Controller  →  Service  →  Repository/Prisma
```

- **Controller:** HTTP only. Parse, validate (via DTO), delegate, shape response. No business logic, no Prisma calls, ever.
- **Service:** all business rules, orchestration, transactions. Framework-agnostic where practical.
- **Repository:** data access. Introduce one only when queries get complex enough to be worth isolating; simple modules may call `PrismaService` from the service directly.

A controller importing `PrismaService` is always a bug.

### DTOs and validation
- Global `ValidationPipe` runs with `whitelist` + `forbidNonWhitelisted`. **Every allowed field must be declared on the DTO with class-validator decorators**, or the request is rejected outright.
- DTOs are input contracts. Never return a Prisma model directly — map to an explicit response shape so schema changes don't silently leak new fields to clients.
- Never expose `passwordHash`, `refreshTokenHash`, or internal IDs in responses.

### Errors
- Throw Nest's built-in HTTP exceptions (`NotFoundException`, `ConflictException`, `ForbiddenException`) from services. The global `HttpExceptionFilter` shapes them to match `ApiErrorResponse` in shared-types.
- Never swallow errors. No empty `catch {}`.
- Error messages are for humans and must not leak internals (stack traces, SQL, provider IDs).
- For "not found" on a resource the caller isn't entitled to see, return **404, not 403** — a 403 confirms the resource exists.

### Async
- `async/await` throughout. No raw `.then()` chains.
- Every `await` that can fail is either handled or deliberately allowed to bubble to the filter.
- Multi-write operations use `prisma.$transaction`. A partial write is worse than a failed one.

### Comments
- Comment **why**, never **what**. The code states what it does.
- Non-obvious business rules, workarounds, and deliberate deviations get a comment. Nothing else does.
- No commented-out code. Git remembers.

### Testing
- Every service with business logic gets unit tests, with the repository/Prisma layer mocked.
- Every new protected endpoint gets an e2e case asserting both the allowed role (`200`) and a denied role (`403`) — mirror the existing auth/RBAC smoke test.
- Test names describe behaviour: `it('rejects a slot that double-books the teacher')`.

### Before considering work done
1. `npm run lint` passes with no new warnings.
2. `npm run build` passes.
3. `npm run test:e2e` passes.
4. No `console.log` left behind — use the Nest `Logger`.
5. If `schema.prisma` changed, a migration is committed alongside it.

## Design patterns

Use a pattern when it removes real duplication or genuinely clarifies intent. **Do not add abstraction speculatively** — a straightforward service with three methods is better than a pattern-heavy one nobody can follow.

**Established in this codebase — follow these:**

| Pattern | Where | Use it for |
| --- | --- | --- |
| **Module (DI)** | Every Nest feature | Encapsulating a feature and its providers |
| **Dependency Injection** | Everywhere | Always constructor-inject. Never instantiate a service with `new`. |
| **Guard (chain of responsibility)** | `JwtAuthGuard`, `RolesGuard` | Authn/authz, tenant scoping |
| **Decorator** | `@Roles` | Attaching declarative metadata to routes |
| **Interceptor** | `LoggingInterceptor` | Cross-cutting request/response concerns |
| **Filter** | `HttpExceptionFilter` | Centralized error shaping |
| **DTO** | All request bodies | Input contract + validation boundary |
| **BFF** | `apps/web/src/app/api/*` | Keeping tokens out of the browser |

**Reach for these when the need is real:**

- **Repository** — when a feature's queries grow beyond simple CRUD, or the same query appears in more than one service.
- **Strategy** — for genuinely interchangeable implementations (e.g. swapping video providers, storage backends). Not for two `if` branches.
- **Factory** — when construction is complex or depends on runtime config.
- **Adapter** — wrap every third-party SDK (video provider, email) behind an interface you own, so the vendor never leaks into your services.
- **Event emitter** — for decoupling genuine side effects (send invite email on user creation). Do not use events to hide a control flow that should be explicit.

**Avoid:**
- Abstract base classes shared across features — they couple unrelated things and are painful to unpick.
- Generic "manager" / "helper" / "util" classes with no cohesive responsibility. Name things for what they do.
- Inheritance where composition works. Default to composition.
- Premature generalization. Duplicate twice before you abstract.

## Cross-cutting API conventions

- Global `ValidationPipe` with `whitelist` + `forbidNonWhitelisted` — see DTO rules above.
- Global `HttpExceptionFilter` (`common/filters`) shapes error responses to match `ApiErrorResponse` in shared-types.
- Global `LoggingInterceptor` logs requests. Both registered in `app.module.ts`.
- `helmet` + CORS (`credentials: true`, origin from `CORS_ORIGIN`) configured in `main.ts`.
- All new endpoints are documented with Swagger decorators — `/api/docs` is expected to stay accurate and is how the mobile client will be built against this API.

## When adding a domain feature

The platform is multi-tenant. Before writing a line of a new feature, confirm:

1. Does every new table carry a non-null `school_id` (or equivalent tenant key) with an FK?
2. Is every query scoped by tenant, enforced centrally rather than remembered per-handler?
3. Does every new controller declare `@Roles` explicitly?
4. Are cross-tenant misses returning `404`, not `403`?
5. Is there an e2e test proving a user of one tenant cannot read another's data?

If any answer is no, the feature is not done.

**Tenant isolation is automatic, not opt-in.** `apps/api/src/prisma/tenant-guard.extension.ts` scopes every query on a tenant-scoped model to the current request's `schoolId` (from `TenantContextService`, `apps/api/src/tenancy/`) and rejects writes carrying a mismatched `schoolId`. New tenant tables must be added to `TENANT_SCOPED_MODELS` in `apps/api/src/prisma/tenant-scoped-models.ts` the same day their migration adds the `school_id` FK — until then the table is invisible to the guard. A route that legitimately needs to cross tenants (platform-only, `SUPER_ADMIN`) must declare `@BypassTenantScope()` explicitly; there is no ambient bypass by role alone. Postgres Row-Level Security as a second line of defence is deferred (see the extension file's header comment) — raw `$queryRaw`/`$executeRaw` against tenant-scoped tables bypass the guard entirely and should be avoided.
