# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## What this is

The **Smart Teacher** platform. Auth, RBAC, multi-tenancy, invites, schools, taxonomy, platform content/entitlements, videos, classes, enrollments and a dashboard shell exist. Timetables do not.

**Prime directive:** mirror the existing NestJS module and Next.js App Router patterns. Do not introduce a new pattern, library, or folder convention when an established one already covers the case. If a new pattern is genuinely warranted, say so and explain why *before* writing code.

## Monorepo layout & commands

npm workspaces + Turborepo. Node 22 (`.nvmrc`). Run scripts from repo root.

| Path | Purpose |
| --- | --- |
| `apps/api` | NestJS + Prisma + PostgreSQL REST API (port 4000). Swagger `/api/docs`, health `/health`. |
| `apps/web` | Next.js App Router + Tailwind (port 3000). |
| `apps/worker` | Transcode consumer: BullMQ + ffmpeg, plain Node (no Nest — it has no HTTP surface). Listens on no port; reports results to the API over an HMAC-signed callback and holds no `DATABASE_URL`. See `apps/worker/README.md`. |
| `packages/shared-types` | `Role` enum + shared interfaces — `@smart-teacher/shared-types`. |
| `packages/tsconfig` | Base TS configs — `@smart-teacher/tsconfig`. |

> **Sync requirement:** the `Role` enum in `shared-types` **mirrors** `apps/api/prisma/schema.prisma` (the source of truth). No codegen — keep them in sync manually.

| Command | Purpose |
| --- | --- |
| `npm run dev` | api + web in watch mode |
| `npm run build` / `lint` | All workspaces |
| `npm run test:e2e` | API e2e auth/RBAC/tenancy suite |
| `npm run db:migrate` / `db:seed` | `prisma migrate dev` (api only) / seed the platform super admin |
| `npm run docker:up` / `docker:down` | Full stack (Postgres + api + web) |

Single test, from `apps/api`: `npx jest --config ./test/jest-e2e.json -t "name substring"`

Prisma client is generated by `postinstall` in `apps/api`, so `npm install` regenerates it. **After editing `schema.prisma`, always run `npm run db:migrate`** and commit the migration alongside it.

## Local dev setup

Postgres in Docker; apps run natively for hot reload.

```bash
cp .env.example .env                    # docker-compose vars (Postgres + container defaults)
docker compose up -d postgres
npm install
cp apps/api/.env.example apps/api/.env  # DATABASE_URL must point at localhost:5432
cp apps/web/.env.example apps/web/.env
npm run db:migrate && npm run db:seed
npm run dev
```

**Two layers of env files.** Root `.env` feeds `docker-compose.yml`; `apps/api/.env` and `apps/web/.env` feed the natively-run apps. The API validates env at boot via `config/env.validation.ts` (class-validator) — a missing/invalid var throws on startup. Use `ConfigService.getOrThrow` downstream; **never read `process.env` outside the config module.**

**`npm run test:e2e` uses a third, isolated database** — `apps/api/.env.test`, pointed at a separate `smartteacher_test` database, never the dev/docker-compose one. `AppModule`'s `ConfigModule.forRoot` picks `.env.test` over `.env` whenever `NODE_ENV === 'test'` (which Jest sets automatically). `test/utils/global-setup.ts` also loads `.env.test` explicitly, first thing, with `override: true` — `@prisma/client` does its own implicit `.env` lookup the moment it's constructed, and since `dotenv` never overrides an already-set var, skipping this step would let that dev `.env` win and silently point e2e writes back at the dev database. Create the test DB once (`CREATE DATABASE smartteacher_test;` on the same Postgres) and run `DATABASE_URL=<test-db-url> npx prisma migrate deploy` from `apps/api` after any new migration — e2e specs create real rows and never clean up, by design, so they must never share a database with `npm run dev` / `docker compose up`.

**The seed creates exactly one account** (`apps/api/prisma/seed.ts`): `superadmin@smartteacher.dev` / `Passw0rd!`, SUPER_ADMIN, no school. It is the only account that cannot be created through the product — a super admin has no tenant, so nobody above them can invite them.

**Nothing else is seeded** — no schools, school users, grade levels, subjects, videos, content entitlements, sections or enrolments. A fresh environment starts empty and an operator creates them through the app, so the seed can never drift from what real onboarding produces. **Do not add fixtures back to `seed.ts`;** they belong in `apps/api/test/utils/`.

**E2e fixtures live in two places, in this order:**

| File | Provides | Runs |
| --- | --- | --- |
| `test/utils/global-setup.ts` | `demo-school` + `demo-school-b`, and one account per role (`admin@`, `teacher@`, `student@`, `admin-b@`, `teacher-b@`) | Once per jest run, via `globalSetup` in `jest-e2e.json` — no spec calls it |
| `test/utils/content-fixtures.ts` | Grade levels `Grade 5`/`Grade 6`, subjects `maths`/`science`, three videos, the entitlement, sections, the student's enrolment | `await seedContentFixtures()` first thing in a spec's `beforeAll`, before `createE2eApp()` |

`global-setup.ts` resets password, role and status on every run rather than using `update: {}` — the auth suites disable accounts, reset passwords and suspend schools, so a run that failed part-way would otherwise poison later runs.

`teacher-b@` exists to prove an unentitled school sees an empty library over HTTP through a non-admin caller; SCHOOL_ADMIN, TEACHER and STUDENT can browse/watch entitled content.

Entitlements in `content-fixtures.ts` are **deliberately asymmetric** — `demo-school` holds exactly one, `(Grade 5, Mathematics)`; `demo-school-b` holds none. Entitlement tests assert that asymmetry, so granting more makes them pass vacuously.

`GET /admin/users` → `200` for SCHOOL_ADMIN, `403` for TEACHER/STUDENT. Reference example of RBAC — copy its shape.

## Auth architecture

Custom JWT auth with Passport strategies. Two token types:

- **Access token** (`JWT_ACCESS_SECRET`, ~15m) — carries `AuthenticatedUser` (`sub`, `email`, `name`, `role`, `schoolId`); trusted directly with no DB lookup (`jwt.strategy.ts`).
- **Refresh token** (`JWT_REFRESH_SECRET`, ~30d) — carries `RefreshTokenPayload` (`AuthenticatedUser` + `jti` + `familyId`). Persisted as a `RefreshToken` row (sha256 hash, never the raw token) rather than one hash column on `User` — that is what makes multi-device sessions and reuse detection possible.

**Rotation with reuse detection** (`auth/refresh-tokens.service.ts`): `POST /auth/refresh` finds the row by `jti`, verifies the hash, marks it `revokedAt`/`ROTATED`, mints a successor in the same `familyId`. Re-presenting a rotated token is either a benign two-tab race or theft:
- Within a 30s grace window **and** prior reason was `ROTATED` → benign, issue a sibling.
- Outside the window, or revoked for any other reason (`REUSE_DETECTED`, `LOGGED_OUT`) → revoke the whole family (`REUSE_DETECTED`), force re-login. The reason check matters: without it, a family killed by theft-detection or logout looks like a normal rotation to the grace check and could be revived.

`POST /auth/logout` revokes just the presented token's family (other devices stay live), or every session for the user if no token is presented (`revokeAllForUser`).

**Login hardening** (`AuthService.validateUser`, `LoginThrottleService`): failures tracked in `LoginAttempt`, keyed by `<schoolSlug>:<email>` (email is unique per tenant, so the key must be too) and separately by IP; 20 failures / 50m locks either key with a `429`. Unknown email and wrong password return the identical `'Invalid email or password'`. Suspended-school and `UserStatus.DISABLED` checks run **after** password verification (so an unauthenticated caller can't probe existence) and are re-checked on **every refresh** — disabling an account takes effect within one access-token lifetime (~15m), not 30 days.

**Forgot / reset password** (`auth/password-reset.service.ts`): `POST /auth/forgot-password` mints a 1-hour single-use token (same mechanics as invites — 256-bit random, sha256 on `User.resetTokenHash`, consumed by nulling it) and **always** returns the identical generic `200` — existing or not, `PENDING`/`DISABLED`, suspended school; only throttling may differ (`429`). Reset requests share `LoginAttempt` under a `reset:` key namespace, so the two limits (20 logins/50m vs. 5 resets/hour) never interact. `POST /auth/reset-password` verifies, then in one `$transaction` updates the hash and revokes every live `RefreshToken` with `PASSWORD_RESET` (a stolen session ends at the reset, not 30 days later) and clears any login lockout on that email — a valid reset token already proves mailbox control.

### RBAC (F-06) — deny-by-default, enforced globally

`JwtAuthGuard` + `RolesGuard` (`common/guards/roles.guard.ts`) are `APP_GUARD`s in `app.module.ts`, so every route is authenticated and role-checked with no per-controller `@UseGuards`. Roles: `SUPER_ADMIN`, `SCHOOL_ADMIN`, `TEACHER`, `STUDENT`.

Every route declares exactly one of:
- `@Public()` — no access token (e.g. `/health`, `/auth/login`). **Method-level only** — guards read it with `getAllAndOverride`, so a class-level `@Public()` would leak to every method on that class.
- `@AnyRole()` — any authenticated user (e.g. `GET /users/me`).
- `@Roles(Role.SCHOOL_ADMIN, ...)` — an explicit allow-list.

**`RolesGuard` fails closed: a route with none of these is denied (403).** It logs an error naming the class and handler, because it can only be a missing decorator, never a client mistake. `getAllAndOverride` means a method-level `@Roles` *replaces* the class list rather than widening it — a narrowing method never silently regains the broader list.

```ts
@Roles(Role.SCHOOL_ADMIN)
export class AdminUsersController { ... }
```

**There is no role hierarchy.** `SUPER_ADMIN` is never implicit — every route admitting it lists it, the same principle as `@BypassTenantScope()` ("no ambient bypass by role alone"). A `SUPER_ADMIN`-reachable route (`schoolId` is `null`) must also carry `@BypassTenantScope()` unless it does no tenant-scoped query, or the tenant guard throws `MissingTenantContextError` (500) — see `users.controller.ts`'s `GET /users/:id`.

**Ownership, beyond role** (`common/authorization/resource-access.ts`): `ResourceAccessPolicy<T>.canRead(actor, resource)` + the `requireReadable(resource, actor, policy, message)` helper collapse "missing" and "not yours" into the same 404 — never leak existence with a 403. Each feature owns its policy in its own folder (`users/users-access.policy.ts` is the reference shape); the caller does one fetch and passes the row through `requireReadable`.

**`apps/api/test/rbac-matrix.e2e-spec.ts` is the living source of truth for route access.** It discovers routes via `DiscoveryService` and fails if a route has no `@Public`/`@AnyRole`/`@Roles`, isn't listed in `MATRIX`, or the table drifts from the decorators. **Adding, removing, or re-scoping a route requires updating `MATRIX` in the same commit.**

### Web ↔ API token flow (non-obvious)

The browser never sees JWTs — the Next.js app is a **BFF**:

1. Login page POSTs to `apps/web/src/app/api/auth/login/route.ts`.
2. That route calls the API (`lib/api-client.ts` → `API_URL`) and stores both tokens in **httpOnly cookies** (`lib/session.ts`), 30-day `maxAge` matching the refresh TTL.
3. Server components (`dashboard/page.tsx`) read the access token from cookies and call the API server-side.
4. `middleware.ts` gates `/dashboard/*`: if the access token is missing or within 30s of expiry it calls `POST /auth/refresh` itself (server components can't set cookies, so this can't be pushed down the tree), writing the rotated pair onto both the in-flight request and the response. Only a missing refresh token or a failed refresh redirects to `/login`.

All web→API access is server-side. `API_URL` is `http://api:4000` in Docker, `http://localhost:4000` locally.

## Folder structure

A new developer should be able to guess a file's location without searching.

### `apps/api` — self-contained feature modules

```
apps/api/src/
├── main.ts, app.module.ts
├── config/                  # env validation, typed config
├── common/                  # cross-cutting ONLY — decorators/ filters/ guards/
│                            #   interceptors/ pipes/ authorization/ — no domain logic
├── prisma/                  # PrismaService + tenant guard extension
├── auth/                    # reference module — copy this shape
└── <feature>/               # schools, users, videos, entitlements, taxonomy, invites…
    ├── <feature>.module.ts / .controller.ts / .service.ts
    ├── <feature>.repository.ts   # only if data access is non-trivial
    ├── dto/                      # create-<feature>.dto.ts, update-<feature>.dto.ts
    ├── entities/                 # response shapes / serializers
    └── <feature>.service.spec.ts
```

- **`common/` is cross-cutting only.** If it references a domain concept, it belongs in that feature's folder.
- A module exports only what others genuinely need — usually the service, never the repository. Cross-feature access goes through the exported service, never another feature's repository or Prisma calls.
- **No barrel `index.ts` inside `apps/api`** — they obscure dependency graphs and break Nest DI ordering. Fine in `packages/*`.

### `apps/web` — App Router

```
apps/web/src/
├── app/
│   ├── (auth)/ (dashboard)/  # route groups for layout boundaries
│   │   └── <feature>/        # page.tsx (server, fetches), loading.tsx, _components/
│   └── api/                  # BFF route handlers only
├── components/ui/            # primitives (button, input, table)
├── components/<shared>/      # composed, reused across routes
├── lib/                      # api-client, session, utils
└── hooks/
```

- **Server components by default.** `'use client'` only for state/effects/browser APIs, pushed as far down as possible.
- Single-route components live in that route's `_components/`; promote to `components/` on second use.
- All API calls go through `lib/api-client.ts`. No raw `fetch` in components.

### Naming

`kebab-case.<type>.ts` (api) · `kebab-case.tsx` (web components) · `PascalCase` classes/components · `camelCase` vars/functions · `SCREAMING_SNAKE_CASE` constants · `snake_case` DB tables/columns via `@map` · booleans prefixed `is`/`has`/`can`.

## Code standards

**TypeScript** — `strict` is non-negotiable. No `any` (use `unknown` and narrow). No `@ts-ignore`; `@ts-expect-error` with a reason only if unavoidable. No non-null `!` — narrow or throw meaningfully. `type` for unions/shapes, `interface` for extendable contracts. Explicit return types on all exports and public service methods.

**Layering (API)** — `Controller → Service → Repository/Prisma`, one-directional.
- **Controller:** HTTP only — parse, validate via DTO, delegate, shape response. No business logic, no Prisma. **A controller importing `PrismaService` is always a bug.**
- **Service:** all business rules, orchestration, transactions. Framework-agnostic where practical.
- **Repository:** introduce only when queries get complex or a query is reused; simple modules may use `PrismaService` directly from the service.

**DTOs & validation** — global `ValidationPipe` with `whitelist` + `forbidNonWhitelisted`, so **every allowed field must be declared with class-validator decorators** or the request is rejected. DTOs are input contracts; never return a Prisma model — map to an explicit response shape so schema changes can't leak new fields. Never expose `passwordHash`, `refreshTokenHash`, or internal IDs.

**Errors** — throw Nest's HTTP exceptions from services; the global `HttpExceptionFilter` shapes them to `ApiErrorResponse`. Never swallow errors; no empty `catch {}`. Messages are for humans and must not leak internals (stack traces, SQL, provider IDs). For a resource the caller isn't entitled to see, return **404, not 403** — a 403 confirms existence.

**Async** — `async/await` throughout, no `.then()` chains. Every fallible `await` is handled or deliberately bubbled to the filter. Multi-write operations use `prisma.$transaction`; a partial write is worse than a failed one.

**Comments** — explain **why**, never **what**. Non-obvious business rules, workarounds and deliberate deviations get one; nothing else does. No commented-out code.

**Testing** — every service with business logic gets unit tests with Prisma mocked. Every new endpoint gets a `MATRIX` row in `rbac-matrix.e2e-spec.ts`. New e2e specs use `apps/api/test/utils/{e2e-app,login}.ts` rather than hand-rolling another bootstrap/login. Test names describe behaviour: `it('rejects a slot that double-books the teacher')`.

**Before considering work done:** `npm run lint` (no new warnings) → `npm run build` → `npm run test:e2e` all pass; no `console.log` (use Nest `Logger`); migration committed if `schema.prisma` changed.

## Design patterns

Use a pattern when it removes real duplication or clarifies intent. **Do not abstract speculatively** — a plain service with three methods beats a pattern-heavy one nobody can follow.

**Established here — follow these:** **Module (DI)** for every Nest feature · **Dependency Injection** always constructor-injected, never `new` · **Guard** (`JwtAuthGuard`, `RolesGuard`, both global `APP_GUARD`s) for authn/authz + tenant scoping · **Decorator** (`@Public`, `@AnyRole`, `@Roles`, `@BypassTenantScope`) for route metadata · **Policy** (`ResourceAccessPolicy` + `requireReadable`) for per-record ownership · **Interceptor** (`LoggingInterceptor`) · **Filter** (`HttpExceptionFilter`) · **DTO** for all request bodies · **BFF** (`apps/web/src/app/api/*`) to keep tokens out of the browser.

**Reach for when the need is real:** **Repository** (queries outgrow CRUD, or repeat across services) · **Strategy** (genuinely interchangeable implementations like video providers or storage — not two `if` branches) · **Factory** (complex or config-dependent construction) · **Adapter** (wrap every third-party SDK behind an interface you own, so the vendor never leaks into services) · **Event emitter** (decoupling genuine side effects like invite email on user creation — never to hide control flow that should be explicit).

**Avoid:** abstract base classes shared across features · generic "manager"/"helper"/"util" classes with no cohesive responsibility · inheritance where composition works · premature generalization (duplicate twice before abstracting).

## When adding a domain feature

The platform is multi-tenant. Before writing a line, confirm — **if any answer is no, the feature is not done**:

1. Does every new table carry a non-null `school_id` (or equivalent tenant key) with an FK?
2. Is every query tenant-scoped **centrally**, not remembered per-handler?
3. Does every route declare `@Public()`/`@AnyRole()`/`@Roles(...)` and appear in `rbac-matrix.e2e-spec.ts`'s `MATRIX`?
4. Do per-record ownership rules go through `ResourceAccessPolicy` + `requireReadable`, not a bespoke check?
5. Do cross-tenant and ownership misses return `404`, not `403`?
6. Is there an e2e test proving one tenant cannot read another's data?

**Tenant isolation is automatic, not opt-in.** `prisma/tenant-guard.extension.ts` scopes every query on a tenant-scoped model to the request's `schoolId` (from `TenantContextService`, `apps/api/src/tenancy/`) and rejects writes carrying a mismatched `schoolId`. New tenant tables go into `TENANT_SCOPED_MODELS` (`prisma/tenant-scoped-models.ts`) **the same day** their migration adds the `school_id` FK — `tenant-model-coverage.spec.ts` fails the build otherwise, and forces every new model to be classified tenant-scoped, platform-global, or deliberately neither. A route that must cross tenants (platform-only, `SUPER_ADMIN`) declares `@BypassTenantScope()` explicitly. Postgres RLS as a second line of defence is deferred (see the extension's header comment) — raw `$queryRaw`/`$executeRaw` bypass the guard entirely, so `raw-sql-guard.spec.ts` fails the build on any use outside its documented allow-list.

**Nested relations are scoped too, with two shapes refused outright.** Prisma's hook fires only for a query's *root* model, so `tenant-scope.util.ts` walks `where`, `include`/`select` and `data`: a to-many include of a tenant-scoped model gets `schoolId` AND-ed into its nested `where`, and relation filters (`some`/`none`) are scoped the same way. Two shapes have no safe rewrite and throw `UnsupportedTenantNestedOperationError` rather than silently pass — a **to-one include** of a tenant-scoped model from a non-scoped parent (a to-one include takes no `where`, so it can't be filtered), and **any nested write** into a tenant-scoped model from a non-scoped parent (`school.update({ where: { id: B }, data: { users: { create } } })` takes its tenant from the parent row, which the guard can't constrain). Write against the child model directly, where stamping and the mismatch check apply.

**Platform content is the reviewed exception to "everything has `school_id`".** `GradeLevel`, `Subject` and `Video` are global, listed in `PLATFORM_GLOBAL_MODELS`; a school reaches them only through `SchoolContentEntitlement`, which *is* tenant-scoped. `ContentEntitlementsService` (`apps/api/src/entitlements/`) is the gate — it takes no school id, because the tenant guard supplies it. SCHOOL_ADMIN, TEACHER and STUDENT may browse/watch entitled content; authoring remains SUPER_ADMIN-only.

**Every content read resolves its scope through `ActorContentScopeService`** (same folder), the one answer to "which curricula may this actor reach?". `VideosAccessPolicy`, `DocumentsAccessPolicy`, and the list services all go through it, so a single-resource read can never be wider than the list; `includes()` derives from `resolve()` for exactly that reason. **STUDENT is narrowed** to entitled STUDENT curricula matching the active enrollment grade. **TEACHER is narrowed leniently**: once a grade-bearing assignment exists, STUDENT curricula must match a taught `(gradeLevel, subject)` pair, while every entitled TEACHER curriculum remains reachable. A teacher with no grade-bearing assignment retains the school-wide entitlement set so legacy onboarding does not blank their library. SCHOOL_ADMIN remains school-wide.

**Playback always reuses that entitlement chain.** `GET /videos/:id/playback-token` calls `VideosService.findPlayableVisibleTo` before minting an ES256 JWT scoped by `vid` and `pfx` to `videos/<id>/`. `PLAYBACK_DELIVERY_MODE=api` points absolute URLs at the existing Nest/MinIO routes for local development; `edge` points them at the Cloudflare Worker/R2 plane. Tokens live for at most ten minutes, and the web player re-mints through its BFF after an authorization failure.

The playback signing private key lives **only in the API**. The edge receives public JWKs and can verify, never mint. `edge/playback-worker/` intentionally sits outside the `apps/*` and `packages/*` workspace globs so Wrangler does not enter the monorepo dependency graph; do not move it under `apps/`.

The cross-tenant grant path is a *separate* service, `ContentEntitlementsAdminService`, reachable only via `EntitlementsAdminController` (`SUPER_ADMIN` + `@BypassTenantScope()`). Keep them apart: `ContentEntitlementsService`'s safety property is that no method accepts a school id, and merging the admin path would put one there.
